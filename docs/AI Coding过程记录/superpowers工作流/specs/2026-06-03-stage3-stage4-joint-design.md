# LabelHub 阶段三/四整体方案设计稿

> 日期：2026-06-03
> 目标：在不再扩散到阶段五的前提下，把 **阶段三剩余收口** 与 **阶段四主线目标** 合并成一套可执行、可验证、可文档化的整体方案。

## 1. 背景与当前状态

当前仓库已经完成了大部分阶段三核心能力，但离“严格按路线图口径完成阶段三，并顺利进入阶段四”还差最后一层统一收口。

### 当前已具备的基线
- 前端 A 侧：
  - 高级模板核心能力已落地：条件显示、基础联动校验、分组容器、多 Tab 布局
  - Reviewer 页面已具备多轮审核记录、diff、时间线展示
  - Owner 页面已有审核标准、Prompt 模板、评分维度、导出字段映射、AI/人工审核记录开关
- 后端 B 侧：
  - 多轮审核状态机、提交版本层、Reviewer 分配、批量审核、时间线接口已落地
  - 导出最小真实闭环已具备：`json / csv`、字段映射、包含 AI / 人工审核记录开关、最小历史列表
  - AI 审核已具备 Celery / Redis 异步链路，可作为导出异步任务的复用样板

### 当前仍未完全收口的阶段三问题
#### A 侧（`PLANROAD-A.md`）
- 模板 schema 版本兼容策略在前端的展示与回显规则仍未明确收口
- 联动、校验、diff 展示的测试与异常态处理仍未补齐
- Reviewer 审核台的信息密度与决策效率还有提升空间，尚未形成“亮点页”

#### B 侧（`PLANROAD-B.md`）
- 状态机合法性测试仍未补齐
- 批量审核、轮次变更、审计时间线接口测试仍未补齐
- AI 审核、人工审核、提交版本之间的关联键设计虽已实现主体结构，但还缺最后的统一口径审视与文档化

### 当前阶段四仍未启动/未完成的主线
#### A 侧阶段四：答辩与产品化交付
- UI 视觉一致性统一
- 1280×800 / 1920×1080 双分辨率适配
- 用户操作手册、演示视频脚本、关键截图、前端架构说明、Designer/Renderer 设计说明、答辩亮点材料
- README 前端章节与演示环境路径的最终回归

#### B 侧阶段四：导出系统增强
- JSONL / Excel 导出
- 异步导出任务
- 导出进度状态
- 导出文件下载
- 阶段四口径的历史列表与 `review_passed` 筛选验收
- 导出格式测试、内容快照测试、导出产物存储与清理策略

## 2. 本方案的总体目标

本方案不再把阶段三和阶段四割裂处理，而是定义成一套“**先收口阶段三，再推进阶段四主线**”的整体执行包。

### 总目标
1. 先把阶段三从“核心功能已做完”推进到“测试、异常态、文档口径也完整闭合”。
2. 在阶段三口径稳定后，再推进阶段四：
   - A 侧进入产品化与答辩材料交付
   - B 侧进入导出系统增强
3. 全程不并入阶段五的 JWT / RBAC / 部署编排主线，避免范围失控。

## 3. 设计原则

### 3.1 稳健优先
- 不因为要做阶段四而回头大改阶段三架构。
- 不把阶段五混入本轮整体方案。

### 3.2 真实能力优先于文档包装
- 只有真实代码、测试、浏览器/API 验证通过后，才允许回写路线图与进度。
- 阶段四中的“答辩交付物”必须建立在真实能力之上，而不是反向包装未完成功能。

### 3.3 先收口再扩展
- 阶段三优先收测试、异常态、兼容展示和文档口径。
- 阶段四优先补“骨架型能力”，尤其是 B 侧异步导出能力，再扩格式和下载。

### 3.4 精准修改
- 阶段三收口只改与测试、兼容和异常态相关的必要文件。
- 阶段四仍按最小闭环切片推进，不做“整包并行大改”。

## 4. 总体执行顺序

整体分成四段，而不是把阶段三/四所有条目同时开工：

### P1：阶段三口径收口
目标：把阶段三从“核心功能完成”提升为“验收口径完整”。

包括：
- A：schema v1/v2 展示与回显规则收口
- A：联动 / 校验 / diff 的测试与异常态补齐
- A：Reviewer 审核台信息密度与效率优化
- B：状态机、批量审核、轮次/时间线接口测试补齐
- B：统一 AI / Review / Version 关联键口径，并写入文档/决策

### P2：阶段四-B 主线——导出系统增强
目标：让导出从“最小真实闭环”升级为“阶段四骨架”。

执行顺序建议：
1. 导出异步化最小闭环
2. `review_passed` 范围筛选验收闭环
3. JSONL / Excel payload 能力
4. 下载产物、历史、进度展示
5. 格式测试、快照测试、存储与清理策略

### P3：阶段四-A 主线——答辩与产品化交付
目标：把前端从“功能完成”推进到“可展示、可说明、可录屏”。

包括：
- UI 统一与双分辨率适配
- 用户操作手册
- 关键页面截图
- 演示视频脚本
- 前端架构说明
- Designer / Renderer 设计说明
- 答辩亮点稿

### P4：统一回归、文档回写与阶段判断
目标：确认阶段三/四的真实边界，并同步路线图、README、progress、decisions、architecture。

## 5. 阶段三收口设计

### 5.1 A 侧收口重点
#### 1. schema v1/v2 兼容展示规则
- 在模板页明确展示当前 schema 版本
- 旧模板按 v1 回显
- 新结构按 v2 回显
- 明确不做复杂迁移器，只做兼容展示与保存口径收口

#### 2. 联动 / 校验 / diff 的异常态和测试
- `visibleWhen` 不满足时，Renderer 和 Workbench 需表现一致
- `required_if` / `min_selected` / `json_valid` 需有定向测试
- diff 在“首轮无上一版本”与“存在上一版本”两种场景都需有清晰空态或展示

#### 3. Reviewer 审核台亮点化
- 在不改后端结构的前提下提升信息密度：
  - 当前阶段
  - 当前轮次
  - 是否可 diff
  - AI 摘要
  - 审核时间线入口
- 优先做布局与信息组织优化，不再引入新状态概念

### 5.2 B 侧收口重点
#### 1. 状态机合法性测试
- 确认 `submitted -> ai_passed/needs_revision -> review_passed` 等合法流转
- 拦截非法审核或非法重提路径

#### 2. 审核相关接口测试
- 批量通过 / 批量打回
- 轮次递增与版本绑定
- 审计时间线顺序与内容

#### 3. 关联键口径统一
- 统一 `Submission 当前态 + SubmissionVersion 历史层 + ReviewRecord 版本绑定 + AIAuditJob/AIAuditResult 当前轮语义`
- 把这套口径写成设计文档与决策记录，避免后续阶段四导出增强时口径漂移

## 6. 阶段四-B 设计：导出系统增强

### 6.1 目标
让导出从当前“同步 complete + JSON/CSV 最小能力”升级为阶段四要求的：
- 多格式
- 异步任务
- 进度/状态
- 下载产物
- 可验证的范围过滤
- 测试与清理策略

### 6.2 设计原则
- 优先复用 AI 的 Celery/Redis 任务模型
- 不为阶段四直接引入复杂外部存储系统
- 先有异步骨架，再加 JSONL / Excel，再加下载与清理
- 字段映射、包含项开关、`review_passed` 筛选继续复用现有 `ExportJob` 快照语义

### 6.3 导出系统的推荐推进顺序
#### 第一段：异步导出骨架
- `POST /exports` 创建 job 后立即入队
- worker 执行真实导出
- 前端改为轮询 job 状态
- `/complete` 不再是主流程依赖

#### 第二段：格式扩展
- 在既有 `build_export_items()` 基础上扩 `jsonl` 与 `excel`
- 保持字段映射逻辑一致
- 保持 `review_passed` / include 开关口径一致

#### 第三段：下载与历史
- 形成稳定下载入口
- 前端显示下载按钮、历史状态、失败状态
- 对“历史列表已存在但尚未达到阶段四口径”的部分做最终验收闭环

#### 第四段：测试与清理策略
- 导出格式测试
- 内容快照测试
- 失败路径测试
- 导出产物落盘与清理策略说明

## 7. 阶段四-A 设计：答辩与产品化交付

### 7.1 目标
把当前已完成的多角色、多题、模板、审核、导出能力转化为可展示、可说明、可交付的前端作品。

### 7.2 三条主线
#### 1. 产品化外观收口
- 统一视觉风格
- 补角色切换入口、未授权页、统计卡片/面包屑等低风险产品化增强项（若不破坏主链路）
- 覆盖 1280×800 与 1920×1080

#### 2. 演示材料沉淀
- 用户操作手册
- 关键截图
- 5–10 分钟演示视频脚本
- 前端亮点与讲稿提纲

#### 3. 架构说明沉淀
- 前端架构说明
- Designer / Renderer 设计说明
- README 前端能力与演示环境路径对齐

## 8. 范围边界

### 纳入范围
- 阶段三剩余测试、异常态、兼容展示、体验收口
- 阶段四-A 产品化与答辩交付物
- 阶段四-B 导出系统增强
- 相应文档、进度、决策、架构记录回写

### 明确不做
- 不并入阶段五 JWT / 密码哈希 / RBAC / 部署编排主线
- 不重构现有模板、审核、导出大架构
- 不把 JSONL / Excel / 下载 / 存储清理在同一小迭代里一次性全上
- 不为了答辩材料而夸大真实能力

## 9. 验证口径

### 阶段三收口验证
- 后端 pytest：状态机、批量审核、时间线、版本绑定
- 前端测试：schema 兼容展示、联动/校验、diff、Reviewer 工作台
- 浏览器验证：Reviewer 多轮审核与模板联动场景

### 阶段四-B 验证
- 后端 pytest：导出异步、格式、范围、失败路径、快照
- 前端测试：导出页轮询、状态展示、下载入口、失败提示
- 浏览器/API：Owner 发起导出并拿到可验证结果

### 阶段四-A 验证
- 浏览器双分辨率验收
- 文档审阅：README / 手册 / 架构说明 / 演示脚本
- 必要时截图留档

## 10. 风险与控制

### 风险 1：阶段三/四边界重新混乱
控制：先做阶段三口径审计与收口，再进入阶段四开发。

### 风险 2：导出系统一步改太大
控制：严格按“异步骨架 → 格式扩展 → 下载历史 → 测试清理”推进，不整包并行。

### 风险 3：答辩材料先行导致文档夸大
控制：所有材料都以真实页面、真实接口、真实测试结果为依据。

## 11. 推荐下一步

这份设计稿确认后，下一步不是直接大包实现，而是先写一份 **阶段三/四整体 implementation plan**，把整体方案拆成可按 `/goal` 执行的任务序列。

# LabelHub 剩余功能缺口一次性收口设计稿

> 日期：2026-06-04
> 范围：在不做演示 / 云部署 / 交付物 / 强安全升级的前提下，一次性补完当前剩余功能缺口；实现上按三个切片推进：Designer + Tab、Workbench 自动保存、认证体验 + Reviewer 局部错误。

## 1. 背景

截至 2026-06-04，项目已经完成：

- schema v2 的后端存储、运行态渲染与基础规则校验
- Labeler 多题 workbench 的真实读取、草稿保存、提交与重提闭环
- JWT 登录、401 清 session 与受保护路由回登录
- Owner 任务页最小 reviewer 分配入口

但当前仍有几处“功能底层已具备、体验层没补齐”的缺口，已经开始影响后续阶段真实完成度：

1. **高级模板 Designer 只有 schema v2 存储与运行态能力，缺少最小可视化编辑 UI**
   - `visibleWhen`
   - `validationRules`
   - `group.children`
   - `tab.children`
2. **Labeler 仍以手动保存为主，缺少真实自动保存**
   - debounce 自动保存
   - 切题前自动保存
   - 自动保存失败反馈
3. **认证体验只收口到“401 清 session + 回登录页”**
   - 还没有统一退出登录入口
   - 还没有显式登录失效提示
   - 会话清理体验不完整
4. **Reviewer 分配仍混用页面级错误提示**
   - reviewer 列表加载失败会污染整页心智
   - reviewer 保存失败也还不是卡片局部反馈
5. **`tab_container` 运行态仍是“全部展开 children”的兜底，不是真正最小 Tab 切换**

本轮目标不是做系统重构，而是把这些剩余缺口按最小可验收方式一次性收口。

---

## 2. 目标

本轮完成后，系统应满足以下目标：

1. **Owner 模板页可最小可视化编辑 schema v2 核心能力**
   - 可配置 `visibleWhen`
   - 可配置 `validationRules`
   - 可给 `group` 添加、查看、删除 children
   - 可给 `tab_container` 添加、查看、删除 tab 与 tab children

2. **Labeler workbench 支持真实自动保存**
   - 当前题答案变更后 debounce 自动保存
   - 切题前先保存，成功后再切题
   - 自动保存失败时停留当前题并提示
   - 手动保存按钮继续保留

3. **认证体验补最小第二轮**
   - 登录后界面存在统一退出登录入口
   - 会话失效后回登录页时显示一次性提示
   - 主动退出与失效退出都清理本地会话状态

4. **Reviewer 分配错误下沉为局部错误**
   - reviewer 列表加载失败只影响当前任务卡片的分配区块
   - reviewer 保存失败只在当前任务卡片提示

5. **`tab_container` 升级为最小 Tab 切换交互**
   - 默认只展示一个激活 tab
   - 可点击切换 tab
   - 被切换 tab 下的 children 才渲染

---

## 3. 范围边界

### 纳入范围
- `OwnerTemplatesPage` 的 schema v2 最小属性编辑 UI
- `Renderer` 的最小 Tab 切换交互
- `LabelerWorkbenchPage` 的自动保存与切题前保存
- 登录后统一退出入口
- 登录页一次性会话失效提示
- `OwnerTasksPage` reviewer 分配局部错误态与局部反馈
- 对应页面测试与构建验证

### 明确不做
- 不做 Designer 重构或递归拖拽画布
- 不做复杂规则 DSL / 表达式编辑器
- 不做 JSON / 可视化双模式规则编辑
- 不做离线草稿、本地缓存恢复、离站保护
- 不做 refresh token、remember me、多标签会话同步增强
- 不做 reviewer 分配模型重构
- 不做强安全升级、部署、答辩物料与演示脚本
- 不做与本轮缺口无关的大规模拆组件或抽 hooks

---

## 4. 方案选择

本轮考虑过三种方案：

### 方案 A：严格最小收口（本轮采用）
- 保持当前页面结构不变
- 在现有页面内补齐缺失功能
- 尽量复用已有 state、API 与组件边界

**优点**
- 改动面最小
- 回归风险最低
- 最符合当前“精准修改、避免重构”的项目约束

**缺点**
- 页面文件不会变小
- 局部逻辑复用性一般

### 方案 B：先局部抽组件 / hooks 再补功能
- 先把 Designer 属性区、Workbench 保存逻辑、Reviewer 分配区块抽出来
- 再做功能补齐

**优点**
- 结构更清楚

**缺点**
- 这轮重点不是重构
- 容易扩大范围并增加测试面

### 方案 C：趁机做半系统化升级
- 顺手把 Designer / Renderer / 权限提示都再抽一层统一模型

**优点**
- 结构更完整

**缺点**
- 明显超出本轮目标
- 容易失控

### 本轮最终采用
**方案 A：严格最小收口。**

原因：当前缺口都已落在已存在的页面和能力上，最合理的方式是在现有边界内做补齐，而不是再启动一轮结构升级。

---

## 5. 切片拆分

虽然本轮目标是“一次性补完剩余功能缺口”，但实现与验证按以下三个切片推进：

1. **Designer + Tab**
2. **Workbench 自动保存**
3. **认证体验 + Reviewer 局部错误**

原因：这三块相对独立，按切片推进可以降低单次修改面，同时保持整体目标不变。

---

## 6. Designer + Tab 设计

## 6.1 现状

当前 `OwnerTemplatesPage` 已具备：

- 组件添加 / 删除 / 排序
- schema 保存与读取
- `visibleWhen` / `validationRules` 的数据透传
- `group` / `tab_container` 的 schema v2 存取

但属性面板还只覆盖：

- 标题
- 字段名
- 必填
- 选项
- `image_upload.maxCount`
- `content`

因此 Owner 虽然能保存 schema v2 数据，但无法通过页面最小可视化地编辑其关键结构。

## 6.2 规则编辑方式

本轮规则编辑统一采用**结构化表单**，不暴露原始 JSON 作为默认入口。

### `visibleWhen`
每条规则最小字段：
- `field`
- `operator`
- `value`（仅对需要值的操作符展示）

操作符沿用当前运行态能力：
- `eq`
- `neq`
- `not_empty`
- `includes`

### `validationRules`
每条规则最小支持当前已有类型：
- `required_if`
  - `field`
  - `operator`
  - `value`
- `min_selected`
  - `value`
- `json_valid`
  - 无额外参数

### 为什么不用 JSON 编辑
- 当前目标是“最小可视化编辑能力”
- 用户已明确偏好结构化表单
- 现有规则类型数量很少，用结构化表单即可覆盖本轮范围

## 6.3 `group.children` 编辑方式

`group` 在属性面板增加一个最小 children 管理区：

- 展示当前 children 列表
- 支持向 group 添加子组件
- 支持删除子组件
- 支持选择某个子组件进入其属性编辑

本轮不做：
- group 内拖拽排序
- group 内独立画布
- 深层递归嵌套可视拖拽

### 数据约定
- `group` 自身继续不使用 `field`
- `children` 里的普通字段组件继续使用现有 `TemplateComponent` 结构
- children 编辑与顶层组件编辑共用同一套最小字段面板

## 6.4 `tab.children` 编辑方式

`tab_container` 在属性面板增加最小 tab 管理区：

- 展示 tab 列表
- 支持新增 tab
- 支持编辑 tab 标题
- 支持删除 tab
- 支持向某个 tab 添加子组件
- 支持删除 tab 中的子组件
- 支持选择 tab 中某个子组件进入属性编辑

本轮不做：
- tab 拖拽排序
- tab 内画布拖拽
- 嵌套 tab

### 数据约定
- 每个 tab 仍保留 `{ key, label, children }`
- 新增 tab 时生成稳定 key
- 至少保留一个 tab，避免空容器造成预览和运行态语义不清

## 6.5 属性编辑状态设计

为了不大改当前 `selectedId` 机制，本轮建议把“当前正在编辑哪个组件”扩展为**最小路径选择语义**：

- 顶层组件：按现有 `selectedId`
- `group` 子组件：记录其父 `group` 与 child id
- `tab` 子组件：记录其父 `tab_container`、tab key 与 child id

这样可以在不重建整个画布结构的情况下，复用当前属性表单，只把“找到目标组件并写回 patch”的逻辑扩展到嵌套路径。

## 6.6 `tab_container` 运行态交互

`Renderer` 中的 `tab_container` 从“全部展开”升级为**最小切换式交互**：

- 默认激活第一个 tab
- 顶部显示 tab 按钮行
- 点击后切换当前激活 tab
- 仅渲染激活 tab 的 children

### 为什么不继续全部展开
- 全展开只解决了“第二个 tab 的字段不可见”问题
- 但不能表达“Tab 容器”真实交互语义
- 题目当前缺口明确要求补“最小 Tab 切换交互”

### 为什么只做最小切换
- 当前范围是运行态补缺口，不是做完整 UI 组件系统
- 本轮不需要记忆刷新后的 tab、也不需要做复杂动画与样式体系

## 7. Workbench 自动保存设计

## 7.1 现状

当前 `LabelerWorkbenchPage` 只有：

- 手动“保存草稿”按钮
- 提交前必要时先补一次 draft 保存
- `autosaveFeedback` 文案状态，但没有自动触发逻辑

因此当前 workbench 仍然偏“手动表单”，而不是“真实标注工作台”。

## 7.2 保存语义

本轮统一约定：**手动保存、自动保存、切题前保存共用同一套保存函数**。

这个保存函数负责：
- 调 `POST /submissions/draft`
- 更新 `itemSubmissionIds`
- 更新当前题本地草稿状态与保存时间
- 返回成功 / 失败结果给调用方

这样可以避免三套保存逻辑分叉。

## 7.3 debounce 自动保存

### 触发条件
- 当前题答案变更后
- 若有真实改动，启动 debounce 定时器
- 在设定时间内没有继续输入时，触发自动保存

### 自动保存结果
- 成功：更新自动保存提示文案
- 失败：显示自动保存失败提示，但不阻断继续编辑

### 状态要求
自动保存应有独立状态，避免与手动保存 / 提交状态混淆：
- 自动保存中
- 自动保存成功提示
- 自动保存失败提示

## 7.4 切题前自动保存

你已确认的语义为：**先保存，成功后再切题；失败则停留当前题并提示。**

因此：
- 点击“上一题 / 下一题”时
- 若当前题有未保存改动，则先触发一次立即保存
- 保存成功后才切题
- 保存失败则：
  - 当前题不切换
  - 页面提示“自动保存失败，请先重试”之类文案

### 为什么不用“先切题再后台保存”
- 这轮目标是减少丢内容风险
- workbench 当前仍是单页受控状态，切题后再失败更难解释
- “先保存再切题”更稳，也更符合课程项目当前阶段的心智预期

## 7.5 手动保存按钮保留

手动“保存草稿”按钮继续保留，作用：
- 显式兜底
- 给用户确定感
- 在自动保存失败后，提供立刻重试入口

### 文案关系
- 手动保存成功：继续保留“草稿已保存”反馈
- 自动保存成功：显示“已自动保存于 xx:xx:xx”
- 两类反馈不要互相覆盖掉关键错误文案

## 7.6 本轮不做
- 不做离线草稿
- 不做本地持久化缓存
- 不做页面关闭前强拦截
- 不做跨题批量保存
- 不做保存冲突解决

## 8. 认证体验设计

## 8.1 目标

当前认证主链路已经正确，但体验不完整。本轮只补最小第二轮：

- 统一退出登录入口
- 登录失效一次性提示
- 会话清理体验收口

## 8.2 退出登录入口

在登录后的主界面提供统一“退出登录”入口。

### 要求
- 任意角色进入受保护页面后都能找到
- 点击后：
  - 清 token
  - 清 role
  - 清本地会话相关临时标记
  - 跳回登录页

### 为什么要统一入口
- 当前虽有被动清 session，但没有主动退出
- 课程项目中多角色切换频繁，没有退出入口会影响联调体验

## 8.3 登录失效提示

你已确认的方案是：**登录页一次性提示。**

因此：
- 某请求返回 401 后
- 现有 API client 继续负责清 session 并触发回登录
- 同时记录一个“一次性失效提示”标记
- 登录页在进入时消费该标记并显示：
  - `登录已失效，请重新登录`

### 为什么不在当前页先提示
- 当前已有统一回登录的机制
- 在当前页提示再跳转，会扩大改动面
- 登录页一次性提示已足够表达状态变化

## 8.4 会话清理体验

会话清理分两类：

### 主动退出
- 用户点“退出登录”
- 清 token / role / 失效提示标记
- 回登录页但不显示“失效”提示

### 被动失效
- 接口 401
- 清 token / role
- 写入一次性失效提示标记
- 回登录页后显示提示一次并消费掉

### 本轮不做
- refresh token
- 自动续期
- remember me
- 多标签同步广播增强

---

## 9. Reviewer 分配局部错误设计

## 9.1 现状

当前 `OwnerTasksPage` 中 reviewer 分配仍使用页面级错误：

- reviewer 列表加载失败 → `pageError`
- reviewer 保存失败 → `pageError`

这会带来两个问题：
- 一个卡片的 reviewer 区块失败，会让整页看起来像全局异常
- 已经成功加载的任务列表会被局部错误打断心智

## 9.2 状态拆分原则

本轮把 reviewer 分配相关状态下沉到**当前卡片局部**，而不是继续挂在 `pageError` 上。

### 页面级错误继续保留给
- 任务列表加载失败
- AI 配置保存失败
- 数据集预览加载失败
- 其他真正影响整个页面的异常

### reviewer 分配局部状态负责
- reviewer 列表加载中 / 失败
- 当前卡片 reviewer 保存中 / 失败
- 当前卡片 reviewer 保存成功反馈

## 9.3 reviewer 列表加载失败语义

当打开某个任务的 reviewer 分配区块时：
- 若 `/users/reviewers` 加载失败
- 只在该分配区块内显示错误与重试入口
- 不影响任务主列表继续可见

## 9.4 reviewer 保存失败语义

当保存某个任务 reviewer 分配失败时：
- 只在当前任务卡片 / 当前分配区块内提示失败
- 不污染其他任务卡片
- 不切断当前编辑上下文

## 9.5 成功反馈

Reviewer 分配成功后：
- 成功提示也尽量局部显示在当前卡片
- 更新任务列表回显 reviewer 摘要
- 关闭当前编辑区块或保持收起，二者择其一，以当前实现最简为准

## 11. 风险与控制

### 风险 1：Designer 嵌套编辑扩大范围
控制：
- 只做 children 列表与最小增删改
- 不做递归拖拽与独立嵌套画布

### 风险 2：自动保存与提交状态互相覆盖
控制：
- 统一保存函数
- 区分自动保存反馈、手动保存反馈、提交反馈

### 风险 3：退出登录与失效提示相互污染
控制：
- 主动退出时清空失效提示标记
- 被动 401 才写入一次性提示

### 风险 4：Reviewer 局部状态和全局 pageError 混用
控制：
- 明确 pageError 只保留真正页面级异常
- reviewer 分配区状态独立管理

---

## 12. 最终结论

本轮采用**严格最小收口方案**，并按三个切片推进：

1. **Designer + Tab**
   - 结构化表单编辑 `visibleWhen` / `validationRules`
   - 最小 children 管理补齐 `group` / `tab_container`
   - Renderer 升级为最小 Tab 切换交互

2. **Workbench 自动保存**
   - debounce 自动保存
   - 切题前先保存后切题
   - 失败留在当前题并提示
   - 手动保存按钮保留

3. **认证体验 + Reviewer 局部错误**
   - 统一退出登录入口
   - 登录页一次性会话失效提示
   - Reviewer 分配错误从页面级下沉到卡片局部

该方案覆盖了当前剩余功能缺口，又避免把本轮工作扩大成重构、部署或强安全升级，符合当前项目阶段与验收边界。

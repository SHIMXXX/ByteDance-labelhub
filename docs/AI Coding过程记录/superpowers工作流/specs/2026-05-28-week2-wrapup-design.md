# 第二周 A+B 收尾设计稿

> 日期：2026-05-28
> 目标：在今天内完成 A 侧前端与 B 侧后端路线图中“第二周”全部未完成内容，且不包含任何设计演示、录屏、答辩包装类工作。

## 1. 背景与问题

当前项目主链路已经基本打通，但 `PLANROAD-A.md` 与 `PLANROAD-B.md` 中仍有若干第二周条目未勾选。问题不完全是“代码没做”，还包括：

- 部分事项实际上已完成，但路线图/进度文档未同步。
- 部分事项只差最小收口，不需要扩到第三周范围。
- A/B 两侧的“第二周完成判定”缺少统一口径，容易一边补代码、一边又把范围做大。

因此今天的任务不是继续泛化开发，而是把第二周范围**收紧、补齐、验证、回写**，让“第二周已完成”这件事在代码、测试、契约、计划文件上都成立。

## 2. 本次收尾目标

今天只完成以下目标：

1. 让 `PLANROAD-A.md` 中第二周未勾选项全部具备完成依据。
2. 让 `PLANROAD-B.md` 中第二周未勾选项全部具备完成依据。
3. 所有完成判定都必须能落到以下至少一种证据：
   - 真实代码能力已存在
   - 自动化测试或最小链路验证已通过
   - 统一接口契约已覆盖
   - 进度文档已同步记录
4. 不提前做第三周体验优化、演示包装、架构升级项。

## 3. 范围边界

### 纳入范围
- A 第二周未勾项逐条核验与补齐
- B 第二周未勾项逐条核验与补齐
- `docs/api-contracts/labelhub-v1.md` 中缺失契约补齐
- A/B 路线图与进度文档同步
- 必要的最小代码修补与验证

### 明确不做
- 演示脚本、录屏、答辩话术、展示包装
- 第三周体验优化与文案打磨
- 超出第二周完成判定所需的重构
- 为了“更完整”而追加的升级项

## 4. 收尾策略备选

### 方案 A：最小闭环收口（推荐）
先核对第二周未勾项，把“已完成但未同步”和“真正未完成”分开；只补阻塞第二周完成判定的最小缺口，最后统一验证与回写文档。

**优点：** 最快、最稳、最符合今天目标。
**缺点：** 不会顺带推进第三周质量提升。

### 方案 B：偏代码补齐
优先把所有疑似未完成能力补到更完整，再回头更新计划。

**优点：** 代码层面更扎实。
**缺点：** 很容易把第二周收尾做成第三周扩展。

### 方案 C：偏文档判定
优先修正计划和完成标准，尽量少动代码。

**优点：** 节省时间。
**缺点：** 如果存在真实缺口，会留下风险。

### 结论
采用 **方案 A：最小闭环收口**。

## 5. A 侧第二周收口设计

A 侧核心不是继续开发新页面，而是收口“真实接口接通 + 契约覆盖 + 判定同步”。

### A 侧重点检查项
1. `前端主要页面已接真实接口`
   - 核实任务列表、新建任务、模板保存/读取、任务广场/领取、草稿保存/提交是否都已有真实接口路径。
   - 若已完成但计划未勾，补证据并回写。
2. `导出接口契约`
   - 在统一契约文档中补齐导出相关字段、状态与响应结构。
3. `登录接口说明`
   - 核实契约文档中 auth 章节是否足以支撑“已完成”判定；若够，直接同步计划；若不够，补最小说明。
4. `任务/模板/提交接口契约`
   - 重点检查是否还存在计划层面说“未对齐”，但契约文档实际上已覆盖的情况。
5. `黄金路径第一次完整可见`
   - 以现有真实链路验证记录为依据判断是否可正式勾选。

### A 侧完成标准
- 第二周所有未勾项都能找到明确证据。
- 除非发现真实缺口，否则优先更新文档而不是新增功能。

## 6. B 侧第二周收口设计

B 侧重点是把仍未勾选的第二周条目，严格按“最小实现即可完成判定”的原则收口。

### B 侧重点检查项
1. `最小调用封装`
   - 核实当前 `AIExecutor` / `DeepSeekAIExecutor` 边界是否已足以支撑该条目标记完成。
   - 若只差文档口径，更新计划；若仍缺最小稳定性，补最小修正。
2. `请求级超时控制`
   - 确认是否已有 timeout 配置或调用边界；没有则补最小实现。
3. `重试计数落库（未实现自动重试）`
   - 保持“只记录 attempt/max_attempts，不做自动 retry”的既有边界，确保计划描述与代码一致。
4. `同步链路内失败转人工复核`
   - 确认提交时 AI 失败后的降级路径已经存在并可验证。
5. `一个 submission 仅持有一条 AI job`
   - 确认唯一约束或等价约束已存在。
6. `完成导出任务创建、状态查询、占位下载地址接口（未完成真实文件生成）`
   - 结合当前真实 JSON/CSV 导出能力，重新判定这条是否应直接视为完成。
7. `黄金路径后端已完整打通`
   - 以当前登录→任务→模板→领取→提交→AI→审核→导出链路证据决定是否勾选。
8. `导出接口契约`
   - 若 A/B 共用同一契约文档，则统一一次补齐。

### B 侧完成标准
- 第二周范围只补最小必要实现，不进入 JSONL / Excel、后台任务系统、异步重构等第三周/升级项。
- 计划中的“未实现自动 retry”表述必须与真实代码一致，不能夸大。

## 7. 联合执行顺序

### 阶段 1：差异盘点
把 A/B 第二周所有未勾项分成三类：
- `已完成但未同步`
- `部分完成，需补最小实现`
- `今天不应纳入第二周完成定义`

### 阶段 2：先收 A 侧
优先补契约和计划同步，因为 A 侧很多项大概率是“实际已完成但未勾”。

### 阶段 3：再收 B 侧
只补真正阻塞第二周判定的最小代码/测试闭环。

### 阶段 4：统一验证
至少完成：
- 相关后端测试
- 必要前端构建或最小验证
- 统一检查契约、路线图、进度文档是否一致

### 阶段 5：文档回写
同步更新：
- `PLANROAD-A.md`
- `PLANROAD-B.md`
- `.claude/context/progress-A.md`
- 如有必要，再更新 `decisions-A.md`

## 8. 风险与约束

### 风险
- 路线图未勾项可能混杂“真缺功能”和“仅未同步”，若不先盘点，容易误做。
- B 侧收尾若不控范围，容易滑入第三周升级项。
- 契约文档若不与实际接口一一对应，最后仍会留下完成度争议。

### 控制方式
- 所有修改都必须能回扣到第二周未勾项。
- 优先修正判定依据，不顺手做额外增强。
- 每完成一项，就立刻补对应证据和文档同步。

# 阶段0剩余项收口 + 阶段1联合推进设计稿

> 日期：2026-05-29
> 目标：在今天内利用多 agent 协同，尽量完成 A/B 端后续阶段 0 剩余内容，同时把后续阶段 1 作为整包任务向前推进，形成可验证的第一轮真实闭环。

## 1. 背景与当前状态

当前 LabelHub 已完成 MVP 主链路：Owner 建任务/模板/发布、Labeler 领取/作答/保存/提交、Reviewer 审核、Owner JSON/CSV 导出都已有真实链路依据。2026-05-29 又完成了阶段 0 第一轮稳定收口：前端已拆为统一登录 + 分角色工作台，后端已补 AI 结果 normalize 与最小 schema 校验，相关测试已有第一轮通过记录。

但从 `PLANROAD-A.md` 与 `PLANROAD-B.md` 看，仍存在两类未完成内容：

1. **阶段 0 剩余稳定项**：会直接影响稳定演示与对外口径的一致性。
2. **阶段 1 大项缺口**：会直接影响“更像题目要求的标注平台”的核心观感与后续升级路径。

因此今天不能只做文案收尾，也不能无边界开新坑，而是要同时完成：
- 把阶段 0 中仍然阻塞稳定演示的事项尽量收完；
- 把阶段 1 推进到一批真实、可跑、可测、可继续扩展的第一轮闭环。

## 2. 今日目标定义

### 2.1 阶段 0 目标
把 A/B 路线图里仍未勾掉、且会直接影响稳定演示的剩余项尽量收完。

A 侧重点包括：
- 错误提示、空状态、loading 状态与状态文案
- 一键初始化演示数据入口的前端说明或联动

B 侧重点包括：
- AI 返回异常时写入可读错误信息，并自动转人工复核
- JSONL / Excel 能力口径收口，避免前后端能力描述不一致
- AI 调用日志第一版
- seed demo 脚本起步

### 2.2 阶段 1 目标
今天对“完成阶段 1”的解释不是把路线图所有条目一次性做到最终态，而是形成一套**第一轮真实闭环骨架**，为下一轮迭代提供稳定基础。

A 侧阶段 1 第一轮闭环目标：
- 模板搭建器升级为左侧物料区 / 中间画布 / 右侧属性面板
- 拖拽排序 / 放置能力起步
- 至少一批新增组件入口（富文本、JSON、上传、LLM 交互中的可行子集）
- 模板预览区与 Labeler 作答页共用同一套 Renderer 的落地起点
- 字段唯一性校验
- ShowItem 对原始题目数据的渲染增强
- Labeler 支持基于原答案修改并重新提交的起点
- 任务广场搜索、筛选、状态标签起点

B 侧阶段 1 第一轮闭环目标：
- `datasets` / `dataset_items` 模型与任务绑定关系起步
- 数据集最小导入接口起步
- item 级草稿 / 提交 / 审核状态结构起步
- 为前端后续对接多题工作台提供真实边界

## 3. 范围边界

### 纳入范围
- 阶段 0 所有仍直接影响稳定演示的剩余项
- 阶段 1 的第一轮骨架与最小真实闭环
- 相关测试、回归验证、接口一致性检查
- 路线图、进度、决策、README、API 文档中与真实能力有关的必要回写

### 明确不做
- 不承诺今天完成阶段 1 所有高级项的最终态
- 不进入完整多轮审核系统、完整 AI 工程化、完整异步导出系统
- 不做与当前目标无关的大规模重构
- 不为了“看起来完整”而引入半成品能力

## 4. 推进方案备选

### 方案 1：激进并行整包推进（推荐）
由主控 agent 把任务拆成多条独立实施线，并行推进阶段 0 收尾与阶段 1 核心骨架。

**优点：** 今天产出最大，符合“不要停、整包往前推”的目标。  
**缺点：** 冲突面大，必须严格控制职责边界与验证闸口。

### 方案 2：先清阶段 0，再串行做阶段 1
先把阶段 0 全部收干净，再开始阶段 1。

**优点：** 风险最小。  
**缺点：** 会明显拖慢阶段 1 的进入速度。

### 方案 3：只优先前端阶段 1，后端只铺边界
优先追求可见体验升级，把后端阶段 1 压成最小准备工作。

**优点：** 页面观感提升最快。  
**缺点：** 后端真实多题模型继续后置，不符合本轮 A/B 同时推进目标。

### 结论
采用 **方案 1：激进并行整包推进**。

## 5. 多 agent 拆分与交付边界

### 5.1 主控：`labelhub-main-agent`
职责：
- 读取题目、A/B 路线图、进度与决策
- 判断当前阶段与本轮优先级
- 把工作拆成多条线并控制轮次推进
- 在每轮结束后决定继续修正、进入下一轮，还是转交文档回写

输出要求：
- 每轮必须明确“做什么 / 谁来做 / 用什么验证 / 何时视为完成”

### 5.2 实施线 A：前端阶段 0 收尾 + Designer / Renderer 升级
执行者：`labelhub-dev-agent`

范围：
- 错误提示、空状态、loading 状态与状态文案收口
- 一键初始化演示数据入口的说明或联动
- 模板搭建器三栏布局
- 拖拽排序 / 放置起步
- 属性面板收口
- 预览区与 Renderer 共用边界
- 字段唯一性校验
- ShowItem 渲染增强

完成标志：
- Owner 模板页不只是静态壳子，而是具备可验证的设计器升级能力

### 5.3 实施线 B：前端阶段 1 业务页增强
执行者：`labelhub-dev-agent`

范围：
- Labeler 基于原答案修改并重新提交
- 任务广场搜索 / 筛选 / 状态标签
- 上传组件前端真实交互起步
- 富文本 / JSON / LLM 组件入口中的可行子集

完成标志：
- Labeler / Owner 页面出现用户可感知的真实体验升级

### 5.4 实施线 C：后端阶段 0 收尾 + 数据集 / 多题模型起步
执行者：`labelhub-dev-agent`

范围：
- AI 异常可读错误写入并转人工复核
- JSONL / Excel 能力口径收口
- AI 调用日志第一版
- seed demo 起步
- `datasets` / `dataset_items` / task 绑定 / item 级状态与最小导入接口起步

完成标志：
- 后端不只是加表，还要形成前端下一轮可消费的真实边界

### 5.5 测试审查线：`labelhub-tester-review-agent`
职责：
- 每轮开发后做功能测试、回归验证、接口一致性检查
- 只输出 `PASS / FAIL / BLOCKED` 与证据

边界：
- 不替开发做实现修复
- 在主控未明确“准备提交本地仓库”前，不进入阶段提交审查模式

### 5.6 文档线：`labelhub-planner-docs-agent`
职责：
- 测试通过后回写 `PLANROAD-A.md`、`PLANROAD-B.md`、`.claude/context/progress-A.md`、`.claude/context/decisions-A.md`
- 必要时同步 README 与 API 文档

边界：
- 只写与真实代码能力一致的内容，不夸大、不提前勾选

## 6. 执行节奏

采用 **两轮制**：

### 第 1 轮：阶段 0 收尾 + 阶段 1 搭骨架
目标：
- 尽量清掉阶段 0 剩余稳定项
- 为阶段 1 建立前后端第一批真实边界

### 第 2 轮：补关键缺口并连成第一批新闭环
目标：
- 基于第 1 轮结果补关键缺口
- 尽量把 Designer / Renderer / Labeler / 数据集起步能力连成可验证闭环

## 7. 验证闸口

### 7.1 每条实施线的基础验证
- 前端：至少覆盖相关页面测试 + build；涉及 UI 主链路的能力，尽量做浏览器级验证
- 后端：至少覆盖相关 `pytest` 用例；新增模型/接口补最小回归测试

### 7.2 独立验证
每条实施线完成后，先做自身验证，再交给 `labelhub-tester-review-agent` 做独立验证。

### 7.3 文档回写前置条件
只有测试线给出 `PASS`，文档线才回写进度；若为 `FAIL` 或 `BLOCKED`，则回到主控重新分派修正。

## 8. 风险与控制方式

### 风险
- 阶段 1 范围大，多个 agent 并行容易冲突
- 若不控制边界，容易在同一轮里滑入高级能力半成品
- 路线图可能被误写成“全部完成”，与真实能力不符

### 控制方式
- 不做无边界重构，优先在现有结构上切清边界
- 阶段 1 的固定优先级如下：
  1. Designer / Renderer 核心骨架
  2. Labeler 重提与广场增强
  3. 后端数据集 / 多题模型起步
  4. 富文本 / JSON / 上传 / LLM 组件深化
- 容易产生跨文件冲突的工作按子域切分，不让多个 agent 同改一块核心文件
- 文档中保留“起步”“骨架”“最小闭环”等限定词，避免夸大

## 9. 完成判定

### 9.1 阶段 0 完成判定
满足以下条件时，才可视为阶段 0 完成：
- A/B 路线图中仍直接影响稳定演示的剩余项被完成，或被明确收口为“不阻塞当前演示”的后续项
- 相关测试或验证证据存在
- 对外口径与实际代码能力一致

### 9.2 阶段 1 已实质推进判定
满足以下条件时，才可视为阶段 1 已实质推进：
- 前端出现可用的新 Designer / Renderer 能力
- Labeler 或 Owner 业务体验有真实升级
- 后端出现可被后续前端消费的数据模型 / 接口增量
- 文档同步记录新增边界、已完成项与未完成项

## 10. 推荐下一步

这份设计稿确认后，下一步不直接进实现，而是先写实施计划，再由主控 agent 按计划拆分任务并进入多 agent 执行。

实施计划应明确：
- 第 1 轮与第 2 轮的具体任务清单
- 每条实施线的文件范围与验证命令
- 每轮结束后的测试与文档回写顺序
- 哪些未完成项要保留到下一阶段，而不是在本轮硬做成半成品

# LabelHub 第 3 天双线并推设计稿

- 日期：2026-05-25
- 目标：在 `SM` 分支同时推进前端真实链路稳定化与后端最小验证，确保第 3 天结束时拿到可重复演示的一条黄金路径。
- 范围：仅覆盖 Day 3 的执行设计，不重写整体 MVP 架构。

## 1. 设计目标

### 1.1 当日目标
- 前端拿到一条可重复演示的真实用户路径。
- 后端完成这条路径对应的关键接口行为校验。
- 若联调中发现字段或状态定义偏差，同步收口到契约文档。

### 1.2 成功标准
- Labeler 至少完成一次真实链路：`任务广场 -> 领取任务 -> 作答页 -> 保存草稿 -> 再次进入 -> 提交`。
- 后端至少完成一轮关键状态一致性检查：领取、草稿覆盖、提交。
- 如接口字段有变化，更新 [docs/api-contracts/labelhub-v1.md](../../api-contracts/labelhub-v1.md)。

## 2. 约束与前提

- 主开发分支固定为 `SM`，`LWH` 仅作参考，不再作为执行分支。
- 今天不扩新功能，不主动推进 AI 审核、导出升级项，只服务于主链路稳定。
- 优先使用现有页面、现有路由、现有真实接口，避免额外抽象和重构。
- 前端本地联调默认依赖 Vite dev proxy 指向 `127.0.0.1:8000`。

## 3. 执行策略

### 3.1 推荐方案
采用“**前台联调主线 + 后台验证副线**”的双线并推策略：

- **A 侧主线**：围绕真实用户路径做浏览器联调和页面修补。
- **B 侧副线**：围绕同一条链路检查接口语义、状态一致性和最小回归覆盖。

### 3.2 选择原因
- 能最快产出可见成果，贴近答辩与演示目标。
- 前后两线围绕同一条链路推进，不容易出现各做各的。
- 一旦联调发现问题，可以立即定位是页面、契约还是后端状态处理。

## 4. A 侧计划

### 4.1 链路现状检查
目标：确认真实链路是否已经基本可通。

操作：
- 从任务广场进入真实任务。
- 验证领取动作是否拿到正确 assignment 信息。
- 验证作答页是否按真实 schema 正常渲染。

验证：
- 浏览器中可以进入真实作答页。
- 请求命中后端真实接口，而不是残留 mock。

### 4.2 联调修补
目标：收口领取、作答、草稿、提交几个关键点。

操作：
- 修正领取后页面跳转或状态展示问题。
- 修正草稿保存反馈、再次进入回填、提交流程中的明显问题。
- 必要时补最小文案或空态，避免用户路径中断。

验证：
- 至少完成一次“领取 -> 保存草稿 -> 再进入 -> 提交”。
- 用户不会因空白页、错误跳转或无反馈而卡住。

### 4.3 演示数据准备
目标：保证链路可重复演示。

操作：
- 准备至少 1 个 Owner 已发布任务。
- 准备至少 1 个 Labeler 可领取样例。
- 确认模板版本冻结后的真实 schema 可持续复现。

验证：
- 重启前后仍能用同一批样例重新演示主链路。

## 5. B 侧计划

### 5.1 接口行为核对
目标：确认主链路关键接口行为和契约一致。

范围：
- `GET /tasks/plaza`
- `POST /tasks/{id}/claim`
- `GET /workbench/items`
- `POST /submissions/draft`
- `POST /submissions/{id}/submit`

验证：
- 字段命名、状态语义、错误返回符合前端当前使用方式。
- `assignmentId`、`submissionId`、schema 读取来源清晰且一致。

### 5.2 状态一致性检查
目标：确认不是“偶然成功”。

重点检查：
- 重复领取时是否符合预期。
- 草稿保存是否覆盖同一提交草稿，而不是意外新增脏数据。
- 已提交内容是否还能重复提交，若不能，返回是否清晰。

验证：
- 至少完成一轮手工或测试层面的状态验证。
- 找到偏差后优先修状态流转，而不是在前端打补丁掩盖。

### 5.3 最小回归覆盖
目标：为当天修复提供最低限度保护。

建议：
- 优先覆盖草稿保存。
- 其次覆盖提交动作。
- 如时间不足，不追求完整状态机测试，但要覆盖当天改动触及的关键点。

验证：
- 相关测试通过，或至少形成可重复执行的验证步骤。

## 6. 联调协作规则

- 任何字段变化先以契约为准，同步更新 [docs/api-contracts/labelhub-v1.md](../../api-contracts/labelhub-v1.md)。
- 若前端问题本质来自后端状态定义不清，优先修后端或契约，不在页面层做长期补丁。
- 若后端行为正确但前端展示断链，优先修页面交互，避免改动无关接口。
- 每完成一个关键修复，都要立即做一次对应链路回放验证。

## 7. 不在今天处理的内容

- AI 审核链路扩展、重试体系升级。
- 导出能力增强或样式优化。
- 无关页面重构、组件抽象、全局样式清理。
- 与主链路稳定无关的功能性升级项。

## 8. 产出物

今天结束前希望至少产出：
- 一条可重复演示的 Labeler 真实黄金路径。
- 一轮关键接口状态一致性验证结果。
- 必要的契约文档更新。
- 必要的最小测试或验证记录。

## 9. 风险与应对

### 9.1 风险
- 前端仍残留 mock 依赖，导致看似成功但未走真实链路。
- 后端状态处理存在隐式分支，导致第二次进入或重复操作异常。
- 演示数据不稳定，导致同一流程无法重复演示。

### 9.2 应对
- 用浏览器网络请求确认真实接口命中。
- 每个关键节点至少做一次重复操作验证。
- 将演示数据准备视作交付物，而不是收尾顺手做。

## 10. 当日验收口径

满足以下三条即可视为 Day 3 达标：
- 前端真实主链路可重复演示。
- 后端关键接口完成最小一致性验证。
- 契约与代码现状没有明显脱节。

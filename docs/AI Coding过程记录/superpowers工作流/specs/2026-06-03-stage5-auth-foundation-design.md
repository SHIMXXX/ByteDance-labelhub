# LabelHub 阶段五子项目一：认证基础层设计稿

> 日期：2026-06-03
> 范围：阶段五第一子项目，只做“真实账号密码登录 + JWT 认证基础层”，不把权限矩阵与部署整包并行推进。

## 1. 背景

当前 LabelHub 虽然已经完成了 Owner / Labeler / Reviewer 三角色主链路、阶段三收口和阶段四导出与交付物增强，但阶段五仍停留在“演示账号 + demo token”模式：

- 后端 `/auth/login` 支持按 `role` 或 `username` 直接登录 demo 用户
- `token_for_user()` 返回硬编码的 demo token
- `get_demo_user()` 通过 demo token 或 `X-Demo-User` 头还原用户
- 前端 `LoginPage` 以三角色卡片直登为主
- `RoleGuard` 仍把 `labelhub_demo_role` 当作关键登录态依据

这套方案适合阶段 1~4 的本地演示，但不适合作为阶段五“认证、权限与部署”的基础：

- 没有真实密码校验
- 没有真实 token 解析
- 权限与资源归属无法建立在可靠认证身份上
- 后续 Docker / Nginx / 云演示时，当前鉴权方案会成为明显短板

因此阶段五必须先落一个**最小真实认证闭环**，再继续做资源权限约束与部署方案。

---

## 2. 目标

本子项目目标是把当前 demo token 登录升级成**真实用户名密码登录 + JWT 认证**，同时保持答辩演示的顺滑体验。

完成后应满足：

1. 后端使用用户名 / 密码完成登录校验
2. 登录成功返回真实 JWT，而不是硬编码 demo token
3. `/auth/me` 能通过 Bearer token 返回当前用户
4. 前端登录页升级为标准账号密码表单
5. 前端保留三角色“演示账号快捷填充”，方便答辩现场演示
6. 路由守卫不再只依赖 `labelhub_demo_role`
7. 后续阶段五第二子项目（资源权限）可以直接基于这个认证基础继续推进

---

## 3. 范围边界

### 纳入范围
- `User` 增加密码哈希字段
- `/auth/login` 改为用户名/密码登录
- `/auth/me` 改为 JWT 当前用户解析
- 统一后端“当前用户获取”依赖
- 前端登录页改成账号密码表单
- 演示账号快捷填充
- `RoleGuard` 适配真实登录语义
- 最小后端 auth 测试
- 最小前端登录 / guard 测试
- 浏览器级最小三角色登录回归

### 明确不做
- 不做注册
- 不做忘记密码
- 不做 refresh token
- 不做多端会话管理
- 不做完整 RBAC
- 不做 Owner / Labeler / Reviewer 资源归属约束
- 不做 Docker Compose / Nginx / 云部署

---

## 4. 方案选择

本轮最终采用：

## 方案 B + 选项 B

即：
- **做完整用户名密码登录页**
- **保留演示账号快捷填充**

### 选择原因

相比“继续角色卡片直登”的过渡方案，这个方案更像真实产品登录入口；
相比“纯账号密码表单”方案，又保留了答辩演示场景下的一键填充便利性。

它在“真实认证基础”与“演示效率”之间取得了平衡。

---

## 5. 后端设计

### 5.1 User 模型调整

在现有 `User` 模型上新增：

- `password_hash`

职责：
- 存储密码哈希
- 登录时完成密码校验

本轮不额外引入独立账号表、认证表或多身份体系，保持模型变更最小。

### 5.2 密码哈希策略

采用当前项目依赖可稳定支撑的最小方案：
- 后端保存哈希值，不存明文密码
- 登录时比对提交密码与哈希

本轮目标不是构建完整账号安全体系，而是确保：
- 演示账号不再绕过密码校验
- 认证链路具备真实密码登录语义
- 为后续权限与部署打基础

### 5.3 JWT 策略

JWT 采用最小闭环设计。

#### payload 最小字段
- `sub`：用户唯一标识（优先使用 username 或 user id）
- `role`
- `exp`

#### 后端能力
- 登录成功签发 JWT
- 请求到达时从 Bearer token 解析用户身份
- `/auth/me` 返回当前用户

本轮不做：
- refresh token
- token 黑名单
- 多设备会话管理
- 复杂 session 生命周期控制

### 5.4 依赖注入与鉴权入口调整

当前 `app/api/deps.py` 中的关键逻辑是：
- `DEMO_TOKENS`
- `token_for_user()`
- `get_demo_user()`
- `require_role()`

本轮重构方向：

#### 保留
- `require_role()`

原因：
- 它仍是后续权限层的重要最小边界
- 可以从“demo 用户角色判断”自然过渡到“JWT 当前用户角色判断”

#### 替换 / 演进
- `get_demo_user()` → JWT 当前用户解析依赖
- `token_for_user()` → JWT 签发函数
- `DEMO_TOKENS` → 移除

原则：
- 不保留“demo token”和“JWT token”双语义并存
- 统一所有后端业务路由的当前用户来源

### 5.5 登录接口设计

#### 当前问题
当前 `/auth/login` 支持：
- `username`
- `password`
- `role`

并且允许只传 `role` 完成 demo 登录。

#### 新设计
本轮改成标准账号密码登录：

##### 请求
```json
{
  "username": "owner_demo",
  "password": "demo-owner-123"
}
```

##### 响应
```json
{
  "code": 0,
  "message": "ok",
  "data": {
    "token": "<jwt>",
    "user": {
      "id": 1,
      "username": "owner_demo",
      "displayName": "Owner Demo",
      "role": "owner"
    }
  }
}
```

#### 错误语义
- 用户不存在 → 401
- 密码错误 → 401
- 缺少用户名或密码 → 400

### 5.6 `/auth/me` 设计

`GET /auth/me`

行为：
- 读取 Bearer token
- 校验 token
- 还原当前用户
- 返回当前用户信息

错误语义：
- 无 token → 401
- 非法 token → 401
- token 对应用户不存在 → 401

### 5.7 演示账号兼容策略

为了保证演示环境可立即使用，不能要求手工改数据库。

因此本轮必须包含一个最小兼容策略：
- 在 schema patch / 初始化路径中，为现有 demo 用户补默认密码哈希
- 保证：
  - `owner_demo`
  - `labeler_demo`
  - `reviewer_demo`
  都能直接登录

本轮目标不是强制用户维护账号体系，而是让现有 demo 用户从“免密码假登录”切换为“有默认密码的真实登录”。

## 6. 前端设计

### 6.1 登录页形态

登录页从“纯角色卡片直登”升级为：

#### 主区
- 用户名输入框
- 密码输入框
- 登录按钮

#### 辅助区
- Owner 演示账号快捷填充
- Labeler 演示账号快捷填充
- Reviewer 演示账号快捷填充

### 6.2 演示账号快捷填充规则

演示账号按钮只负责：
- 填充用户名
- 填充密码

不会直接登录。

也就是说：
1. 点击某个演示账号按钮
2. 表单自动填入演示账号用户名 / 密码
3. 用户点击“登录”

这样做的好处：
- 仍保留真实账号密码登录的产品语义
- 后端不需要保留“按角色直接登录”的特殊入口
- 页面体验和正式登录结构保持一致

### 6.3 登录成功后的本地状态

当前前端依赖：
- `labelhub_token`
- `labelhub_demo_role`

本轮设计调整为：

#### 保留
- `labelhub_token`

#### 弱化
- `labelhub_demo_role`

新的主语义：
- token 是唯一登录凭证
- role 来源于后端登录返回的 `user.role`
- 前端可以把 role 存本地用于轻量跳转和恢复，但不能再把它当作比 token 更可靠的身份来源

### 6.4 登录成功后的跳转

保留现有角色首页：
- owner → `/owner`
- labeler → `/labeler`
- reviewer → `/reviewer`

这样可以最大限度减少本轮改动范围，并与现有演示脚本保持一致。

### 6.5 路由守卫设计

当前 `RoleGuard` 的问题在于：
- 它把 `labelhub_demo_role` 作为核心依据
- 这与真实 JWT 登录语义不一致

本轮守卫逻辑建议：

1. 若没有 token → 跳回 `/`
2. 若有 token，则读取本地保存的当前用户 role
3. 若当前 role 与目标路由不匹配 → 跳到对应角色首页
4. 若匹配 → 放行

本轮不强制在每次页面刷新时统一调用 `/auth/me` 做全局恢复。
原因：
- 这会把“认证基础层”扩展成“完整会话管理”
- 会显著放大改动范围

因此这轮更偏向：
- 登录时拿到 `token + user`
- 本地保存最小必要信息
- Guard 先基于本地状态工作
- `/auth/me` 作为校验与后续扩展入口

### 6.6 登录错误与交互反馈

登录页至少需要明确区分：
- 用户名或密码错误
- 后端未启动 / 网络异常
- 登录中状态

这样既更接近真实产品，也有利于答辩演示中的可解释性。

## 7. 测试设计

### 7.1 后端测试

#### auth 接口测试
至少覆盖：
- 正确用户名/密码可登录
- 错误密码返回 401
- 不存在用户返回 401
- `/auth/me` 在合法 JWT 下返回当前用户
- 无 token / 非法 token 返回 401

#### 角色守卫回归测试
至少覆盖：
- owner token 不能访问 reviewer-only 接口
- reviewer token 不能访问 owner-only 接口
- labeler token 不能访问 owner/reviewer-only 接口

本轮不要求把资源归属约束全部做完，但至少确保角色门没有退化。

#### demo 用户兼容测试
验证三类演示账号在补齐密码哈希后都可成功登录。

### 7.2 前端测试

#### LoginPage 测试
至少覆盖：
- 用户名 / 密码输入可提交
- 点击演示账号按钮可自动填充表单
- 登录成功后保存 token 并跳到对应角色首页
- 登录失败时出现明确错误提示

#### RoleGuard 测试
至少覆盖：
- 无 token 时回登录页
- token + role 匹配时放行
- role 不匹配时跳到正确角色首页

### 7.3 浏览器验收

最少走通三条：
- Owner 登录成功进入 `/owner`
- Labeler 登录成功进入 `/labeler`
- Reviewer 登录成功进入 `/reviewer`

## 8. 风险与控制

### 风险 1：JWT 改造导致整站都 401
控制：
- 先补 auth 测试
- 再改依赖注入
- 最后做浏览器登录回归

### 风险 2：前端仍残留旧 demo role 逻辑，导致登录态分裂
控制：
- 本轮明确弱化 `labelhub_demo_role`
- Guard 改为基于 token + 登录返回 role 的最小真实语义

### 风险 3：demo 用户没有密码哈希，导致本地演示全失效
控制：
- 启动 patch / seed 路径为 demo 用户补默认密码哈希
- 确保三类演示账号都立即可用

### 风险 4：把子项目 1 做成完整账号系统
控制：
- 明确不做注册、refresh token、找回密码、多端会话
- 严格把目标限定在“认证基础层”

## 10. 对后续阶段五的衔接

本子项目完成后，阶段五第二子项目就能自然推进：
- Owner 只能管理自己的任务 / 模板 / 数据集 / 导出
- Labeler 只能访问自己的 assignment / submission
- Reviewer 只能审核被分配或允许可见的任务

也就是说，这一轮不是阶段五的全部，而是后续权限与部署能力的地基。

---

## 11. 一句话总结

本设计选择把阶段五第一步定义为：

**用真实用户名密码 + JWT 替换当前 demo token 登录，同时保留演示账号快捷填充，以最小代价完成从“课程演示登录”到“真实认证基础层”的升级。**

- 日期：2026-05-31
- 目标：补全 A/B 两侧阶段 0 剩余工作，完成阶段 1 全部工作，并在本地跑通“数据集导入 → 建任务 → 多题作答 → 审核 → 导出”的真实链路

## 1. 设计目标与完成定义

### 1.1 总目标
本轮不是做零散补丁，而是将当前 MVP 从“单任务单提交、低配设计器、最小导出链路”升级到更贴近题目要求的真实标注平台形态。

必须同时完成：
- A 侧阶段 0 剩余项
- B 侧阶段 0 剩余项
- A 侧阶段 1 全部未完成项
- B 侧阶段 1 全部未完成项
- 本地真实运行与验证
- 文档、路线图与代码能力一致

### 1.2 完成定义
仅当以下条件全部满足，才视为本轮完成：
- `PLANROAD-A.md` 中阶段 0 / 阶段 1 相关未勾项已被真实代码、测试或文档能力覆盖
- `PLANROAD-B.md` 中阶段 0 / 阶段 1 相关未勾项已被真实代码、测试或文档能力覆盖
- 本地能跑通一条真实主链路：数据集导入 → 任务绑定数据集 → Labeler 多题作答 → Reviewer 审核 → Owner 导出
- 前后端接口、README、进度记录、决策记录不夸大当前能力

### 1.3 本轮不扩展的范围
本轮只收口阶段 0 / 1，不提前进入后续阶段：
- 不做多级人工审核
- 不做 AI 异步队列/自动重试系统
- 不做 JSONL / Excel 导出能力闭环
- 不做复杂条件显示、分组容器、Tab 布局
- 不做完整产品化权限系统

## 3. 总体方案与执行策略

### 3.1 推荐方案
采用“一次性总攻，按主链路分批自动滚动”的方式推进：
1. 先完成 B 阶段 0 剩余与 B 阶段 1 数据底座
2. 再完成 A 阶段 0 剩余与 A 阶段 1 前台升级
3. 再做前后端联调与异常收口
4. 最后在主工作区做本地运行验证与文档回写

这样既满足“目标一次做完”，也保留每轮可测试、可止损的边界。

### 3.2 自动执行边界
按 `labelhub-main-prompt.md` 进入自动执行模式，但保留以下止损条件：
- 连续 2 轮任务 FAIL / BLOCKED → 暂停并向用户汇报
- 单轮修正循环最多 3 轮
- 开发 Agent 允许隔离 worktree 并行开发
- 测试、文档更新、本地运行验证只能在主工作区完成

## 4. 架构设计

### 4.1 后端边界调整
后端从“单 submission MVP”升级为“任务绑定数据集、多 item 标注”的模型：
- 新增 `datasets`
- 新增 `dataset_items`
- `tasks` 支持绑定数据集
- `assignments` 表示一个人领取了一个任务实例
- `submissions` 改为 item 级作答实体
- 新增导入服务，支持 JSON / JSONL / Excel
- 提供任务维度、assignment 维度、item 维度的聚合状态

原则：尽量在现有 auth / review / export 稳定基线上扩展，不推翻第二周已验证能力。

### 4.2 前端边界调整
前端拆成三个清晰子域：

#### Designer
- 左侧物料区 / 中间画布 / 右侧属性面板
- 使用 `dnd-kit` 负责排序 / 放置
- 新组件采用最小可用配置，不做复杂联动系统

#### Renderer
- 抽成预览与作答共用的统一渲染核心
- 统一消费模板 schema 与题目原始数据
- 避免设计器预览与 Labeler 作答长期分叉

#### Workbench
- 从单题视角切到多题工作台
- 提供题号导航、状态、切题、进度、提交前汇总
- 支持打回后基于原答案修改并重新提交

### 4.3 A/B 接口边界
后端负责：
- 数据集导入、预览、分页、搜索
- 任务绑定数据集
- item 级草稿读写与提交
- 聚合状态口径
- 导出聚合结果

前端负责：
- Designer / Renderer / Workbench 交互实现
- 不自行推导复杂聚合口径
- 不暴露后端未提供的配置项
- 严格消费契约允许字段

## 5. 核心数据流

### 5.1 数据集导入
1. Owner 上传 JSON / JSONL / Excel
2. 后端解析生成 `dataset + dataset_items`
3. 返回导入摘要、错误报告、样本预览

### 5.2 任务绑定数据集
1. Owner 创建任务时选择模板与数据集
2. 发布后冻结模板版本
3. 任务读取的数据集保持明确绑定口径

### 5.3 多题作答
1. Labeler 领取任务
2. Workbench 拉取 item 列表与聚合进度
3. item 级保存草稿 / 提交 / 打回后重提
4. 提交前支持未完成校验与汇总提示

### 5.4 审核与导出
1. Reviewer 按 item 或 submission 维度查看真实答案与 AI 结果
2. Owner 导出按任务聚合 item 级结果
3. 当前阶段继续以 JSON / CSV 稳定为主，但底座要兼容后续扩展

## 6. 状态流转设计

### 6.1 任务级状态
`draft -> published -> paused -> closed`

### 6.2 item 作答级状态
`draft -> submitted -> needs_revision -> review_passed`

### 6.3 AI 决策级状态
`pass | human_review | reject`

映射规则保持不变：
- `pass` / `human_review` -> Reviewer 待审
- `reject` -> 待修改

### 6.4 聚合状态口径
由后端统一输出：
- 总题数
- 已保存草稿数
- 已提交数
- 待修改数
- 已通过数
- 完成进度

前端仅展示，不自行重算复杂业务状态。

## 9. Agent 分工

### 9.1 开发 Agent
- 唯一允许修改业务代码
- 可在隔离 worktree 并行处理独立开发块
- 只接受单轮明确范围、修改边界和验收标准

### 9.2 测试与审查 Agent
- 仅在主工作区执行
- 给出 PASS / FAIL / BLOCKED 稳定结论
- 重点检查接口一致性、类型安全、空数据和主链路回归

### 9.3 计划与文档 Agent
- 维护 `PLANROAD-A.md`、`PLANROAD-B.md`、`progress-A.md`、`decisions-A.md`、`architecture-A.md`、README 与契约文档
- 不把未完成能力写成已完成

## 10. 风险与控制

### 10.1 主要风险
- 多题模型会同时牵动 submissions / reviews / exports，联动面大
- Designer 升级与 Renderer 共用化会触及较多前端结构
- JSONL / Excel 导入如果做得过深，可能拖慢主链路收口

### 10.2 控制策略
- 优先完成真实主链路，再补非阻塞增强
- 保持状态机简单，不额外引入阶段 2 / 3 语义
- 每轮都必须先测试再进入下一轮
- 连续 2 轮 FAIL / BLOCKED 停止自动执行并暴露问题
